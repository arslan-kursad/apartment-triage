### Bug 1 — `Results.Forbid()` authentication crash

**Semptom:** `GET /api/webhook/whatsapp?hub.mode=subscribe&...` → HTTP 500, body yok.
Log'da istek hiç görünmüyor (Serilog request logging'e ulaşmıyor).

**Root cause:** `VerifyWebhook` handler, token eşleşmediğinde `Results.Forbid()` çağırıyordu.
`Results.Forbid()` internally `IAuthenticationService`'e bağlıdır.
`AddAuthentication()` kayıtlı olmadığı için DI `InvalidOperationException` fırlatıyor.
Exception, response yazılmadan patlıyor → ASP.NET Core 500 dönüyor, Serilog middleware'e hiç girmeden.

**Ek etken:** `WhatsApp__WebhookVerifyToken` Fly secret değeri yanlış set edilmişti
(`triage_webhook_secret_2026` değil). Token mismatch → her istekte `Results.Forbid()` → her seferinde 500.

**Fix:** `Results.Forbid()` → `Results.StatusCode(403)` (commit `12d9280`).
Ardından secret güncellendi: `fly secrets set WhatsApp__WebhookVerifyToken="triage_webhook_secret_2026"`.

**Sonuç:** Curl → `test123` / HTTP 200. Meta webhook "Verified" ✅.

**Mimari not:** `Results.Forbid()` / `Results.Challenge()` / `Results.SignIn()` authentication
pipeline'ı gerektirir. Auth-less Minimal API'de 4xx için `Results.StatusCode(N)` kullan.

### Bug 2 — `WhatsAppConsumerJob` DI'a kayıtlı değil

**Semptom:** Meta'dan gerçek mesaj geldi, `"WhatsApp webhook: enqueued 1 message(s)"` logu görüldü.
Ama ticket oluşmadı. Hangfire dashboard'da `whatsapp-consumer` job Failed/retry loop'ta.

**Mimari anlama:**

```
[Meta Cloud API]
    → POST /api/webhook/whatsapp
    → WhatsAppWebhookEndpoints.ReceiveMessage()
    → WhatsAppAdapter.TryEnqueue(incoming)      ← in-memory Channel<IncomingMessage>
                                                   (Singleton, Bounded 1000)

[Hangfire, Cron.Minutely()]
    → WhatsAppConsumerJob.RunAsync()
    → channel.ReadMessagesAsync()               ← aynı Singleton'ın Channel'ını okur
    → ProcessIncomingAsync()
    → DB persist → orchestrator → reply
```

Köprü: Her iki taraf da aynı `WhatsAppAdapter` Singleton'ını kullanır.
Webhook yazar (`TryEnqueue`), Hangfire job okur (`ReadMessagesAsync`).
In-memory olduğu için app restart'ta kaybedilir — bu day 15 scope'u dışında.

**Root cause:** Program.cs'de `WhatsAppConsumerJob` DI'a kayıtlı değildi.

```csharp
// Program.cs
builder.Services.AddTransient<ChannelConsumerJob>();      // ✅ Telegram
// builder.Services.AddTransient<WhatsAppConsumerJob>();  // ← YOKTU
```

Hangfire bir job çalıştırmadan önce `serviceProvider.GetService<T>()` ile instance üretir.
Tip kayıtlı değilse `null` döner → `NullReferenceException` → job Failed → retry loop.

İkinci katman: Constructor'da `[FromKeyedServices(ChannelType.WhatsApp)] IMessageChannel channel` var.
Bu attribute ancak DI üzerinden resolve edilince çalışır. `ActivatorUtilities.CreateInstance` veya
direkt `new` ile üretilirse keyed service attribute'u görmezden gelinir — yanlış (veya null) instance inject edilir.

**Fix:** Tek satır (commit `02a2c3b`):

```csharp
builder.Services.AddTransient<WhatsAppConsumerJob>();
```

DI'a kayıtlı olunca container `[FromKeyedServices]` attribute'unu okur,
`AddKeyedSingleton<WhatsAppAdapter>(ChannelType.WhatsApp)` kaydından doğru instance'ı çeker.

### Bug 4 — Verify ≠ Subscribe (Meta webhook iki adım)

Webhook URL verified oldu ama mesajlar gelmiyor gibiydi.
Meta'nın iki adımı birbirinden bağımsız:
1. **Verify** — URL doğruluğunu test eder (hub.mode=subscribe handshake).
2. **Field subscription** — hangi event türlerinin (messages, statuses vb.)
   gönderileceğini aktive eder. Ayrı adım, ayrı kaydet.

Verify başarılı ama field subscription tamamlanmadan mesaj gelmez.
Bunu karıştırmak yaygın bir debug tuzağı.
